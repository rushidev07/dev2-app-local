# PDPRevamp — files and modules used but not owned by this module

This module (`code/Ahy/PDPRevamp`) does not work standalone. It reads from,
overrides, or otherwise depends on the files and modules listed below, none
of which live inside `code/Ahy/PDPRevamp`. If this module is ever moved,
exported, or audited on its own, everything on this page needs to exist
alongside it.

Generated by grepping the module's actual `use` statements, `$this->helper()`
calls, and layout XML — not from memory. Re-run the same sweep if this list
needs refreshing after further changes.

**Formerly listed here, now resolved (2026-08-17):** PDPRevamp used to call `Ahy\ThemeCustomization\Helper\Data::getImageResizeService()` from `gallery.phtml`. That method (plus its private `recoverMissingImage()` localhost fallback) has been moved into this module as `Ahy\PDPRevamp\Helper\Data` and deleted from `Ahy_ThemeCustomization` — confirmed via repo-wide grep that no other module called it. `details-description.phtml` also referenced the ThemeCustomization helper but never actually called a method on it (dead assignment); that line was removed rather than repointed.

**Caution:** `design/frontend/Ahy/Everest2/Magento_Catalog/templates/product/view/gallery.phtml` (theme file, not owned by this module — see §5) still contains a call to the now-deleted `getImageResizeService()`. It is currently dead code — both the theme's own `catalog_product_view.xml` and this module's layout point `product.media` at `Ahy_PDPRevamp::product/view/gallery.phtml` instead, so the theme file isn't rendered by any active layout. If that ever changes (e.g. a store-view layout override reverts to the vendor/theme default), it will fatal. Not fixed here per the own-module-only rule — flagging so it isn't a surprise later.

**Topically related but NOT actually wired into PDPRevamp's code** (worth knowing, since it's easy to assume a connection that doesn't exist):

No code changed pending that call — this is a known gap, not an oversight.

## 4. Theme/vendor templates this module overrides via plugin

These plugins live in `Plugin/*TemplatePlugin.php` and exist specifically because
theme layout XML is merged *after* module layout XML, so a plain
`referenceBlock` template change from this module would be silently
overwritten. Each plugin swaps the template at render time instead. The
original file it replaces is not part of this module and must keep existing
for the block class itself (and its PHP logic) to still work:

| Original template (not owned by PDPRevamp) | Overridden by | Swapped to |
|---|---|---|
| `vendor/hyva-themes/magento2-default-theme/Magento_Catalog/templates/product/view/gallery.phtml` | `Plugin/GalleryTemplatePlugin.php` | `Ahy_PDPRevamp::product/view/gallery.phtml` |
| `vendor/hyva-themes/magento2-default-theme/Magento_Swatches/templates/product/view/renderer.phtml` | `Plugin/SwatchRendererTemplatePlugin.php` | swatch renderer template within this module |
| `vendor/magento/module-theme` (`Magento\Theme\Block\Html\Breadcrumbs`, retemplated by Hyva's `product_breadcrumbs` block) | `Plugin/BreadcrumbsTemplatePlugin.php` | `Ahy_PDPRevamp::product/view/breadcrumbs.phtml` (PDP only — see §5) |
| `vendor/hyva-themes/magento2-default-theme/Magento_Catalog/templates/product/{product-detail-page,view/product-info,view/quantity,view/addtocart,view/addtowishlist,view/product-form}.phtml` (same vendor `Magento\Catalog\Block\Product\View` class — `product.detail.page` resolves to `Ahy\BuyBox\Block\Product\View`, a sibling module's subclass of it, still covered since plugins on a base class apply to subclasses) | `Plugin/ProductViewTemplatePlugin.php` | matching `Ahy_PDPRevamp::...` templates |

**Resolved (2026-08-18):** these 6 templates, plus `product.info.stockstatus` and
`product.yotpo.review.js`, used to be wired in by directly editing
`design/frontend/Ahy/Everest2/Magento_Catalog/layout/catalog_product_view.xml`
(the theme's own PDP layout) rather than via a plugin — the only one of the 9
blocks in §6 that had this problem; `product.media` and the breadcrumb already
used the plugin pattern. That direct-edit approach was confirmed to actually
drift out of sync between environments (a local test install was found
running the old, non-revamped templates for all of these except the two
plugin-covered ones). Fixed by: adding `ProductViewTemplatePlugin` for the six
template-only swaps above; moving `product.info.stockstatus`'s declaration
(needs a real class change, `Ahy\PDPRevamp\Block\Product\View\StockStatus` —
not swappable via plugin) into this module's own `referenceBlock
name="product.info"`; and moving `product.yotpo.review.js`'s declaration
(no vendor layout declares this block name at all) into this module's own
`referenceContainer name="before.body.end"`. The theme's layout XML now only
declares the base page structure with stock `Magento_Catalog::...` templates —
nothing PDPRevamp-specific remains there to drift out of sync again.

## 5. Sitewide files this module deliberately does NOT touch

Worth listing so nobody assumes these were updated as part of the PDP revamp:

- `design/frontend/Ahy/Everest2/Magento_Theme/templates/html/breadcrumbs.phtml` — the sitewide breadcrumb (category/CMS/search pages). `BreadcrumbsTemplatePlugin` only swaps the template when `getFullActionName() === 'catalog_product_view'`, so this file still renders everywhere else, with the old styling. Category/CMS pages currently look visually different from the PDP breadcrumb as a result.
- `design/frontend/Ahy/Everest2/Magento_Theme/templates/html/footer.phtml` — untouched.
- `design/frontend/Ahy/Everest2/web/tailwind/components/swatches.css`, `web/css/styles.css` — sitewide compiled Tailwind CSS this module's templates rely on classes from, but does not own or regenerate. A missing utility class here (e.g. after a Tailwind purge) will silently no-op in a PDPRevamp template with no error.

## 6. Layout containers/blocks this module assumes already exist

`view/frontend/layout/catalog_product_view.xml` hooks into these container/block
names via `referenceBlock`/`referenceContainer` rather than declaring them —
if the module or theme that originally defines one of these is ever removed,
the corresponding PDPRevamp block silently stops rendering:

`head.additional`, `product.media`, `product.info.details`, `addtocart.shortcut.buttons`,
`product.info`, `product.detail.page`, `product.yotpo.review.js`,
`amrelated_product_content_bottom` (from `Amasty_Mostviewed`), `page.top`, `before.body.end`.
